# 4.1.0 — en développement (branche `feature/4.1.0-lexical`, 2026-11-21)

État : **non publiée, non déployée, non qualifiée**. Aucun GO de publication ni de bascule. Cette note
décrit ce que contient la branche ; elle ne revendique aucun gain mesuré.

- **Profil de récupération explicite.** `Config.retrieval_profile` vaut `semantic` (défaut, moteur
  inchangé) ou `lexical` (`Config.lexical()`, `MEMORY_V4_RETRIEVAL_PROFILE=lexical`). Le profil n'est
  jamais déduit des dépendances installées ; `use_dense=False` seul reste le profil sémantique.
- **Profil lexical** (politique `lex-4.1.0-v1`) : BM25 littéral par périmètre, canal d'entités, fusion `cc`,
  garde C4 ; aucun encodeur, aucun vecteur, aucun import de `torch`, `sentence-transformers`,
  `transformers` ni `faiss`. SQLite uniquement. Les options qui changeraient le classement sont refusées.
- **Marqueur et refus avant toute ouverture mutante.** Un store lexical porte
  `retrieval_profile = {"name": "lexical", "policy": "lex-4.1.0-v1"}` dans ses métadonnées ; un store sans
  marqueur est sémantique. Une sonde en lecture seule refuse, sans rien modifier, un store de l'autre
  profil, un marqueur invalide, un store lexical portant des traces sémantiques, ou un store dont le profil
  ne peut pas être lu. Aucune conversion implicite, aucun outil de conversion.
- **Pas de retour arrière 4.0.x pour un store lexical.** Une 4.0.x ouvrirait un store lexical, l'encoderait
  et le marquerait sans avertir ; la 4.1.0 le détecte ensuite et le refuse. Revenir à une 4.0.x suppose de
  reprendre le store sémantique ou la sauvegarde d'avant 4.1.0.
- **Empaquetage.** La fermeture ML (`torch`, `sentence-transformers`, `transformers`, `faiss-cpu` et leurs
  dépendances propres) passe dans l'extra `[semantic]` ; les métadonnées du paquet portent des bornes
  compatibles ; les verrous exacts restent dans les fichiers de contraintes du runtime qualifié, un par
  profil. Installation sémantique : `memory-os-ai[semantic,ops,brief]`.
- **Inchangés** : schéma SQLite 8 et ses sommes, `embed.py` (octet pour octet), clés et codec du cache
  d'embeddings, comportement du profil sémantique.
- **Installation multi-clients (phase 1a-setup, branche `feature/4.1.0-setup`).** `quickstart --profile
  {lexical,semantic}` : profil obligatoire pour une installation neuve (décision R1 en attente de Romain :
  implémentation provisoire de la recommandation), relu d'un service existant, jamais converti ; le service
  lexical ne porte aucune variable d'encodeur et ne télécharge que la table du tokenizer ; le service
  sémantique est identique à l'octet près à celui de la 4.0.9. SQLite chargé vérifié avant toute écriture
  (`ops/sqlite_runtime.py`) et attesté par le serveur (`capabilities.store.sqlite_version`). Codes de refus
  stables. Une entrée cliente existante n'est jamais écrasée en silence (forme reconnue, identité de
  destination, preuve par journal de confiance, consentement nommé `--replace-existing`). Diagnostics
  structurés à liste blanche : plus aucune queue de log, sortie de sous-processus ni détail `doctor`
  journalisé. `quickstart --undo <stamp> --with-service` (arrêt confirmé avant déplacement du plist) et
  `memory-os-admin uninstall` (entrées prouvées, service conservé tant qu'une entrée peut en dépendre,
  données jamais supprimées, aucune purge, jamais « complète »). Localisateur `memory-os-constraints`
  (bibliothèque standard seule) et installation en deux commandes `pip` sous contraintes ; portes de
  résolution par profil. Aucun paquet `.mcpb` (R7 : option C, provisoire). Aucun rattachement d'un store
  conservé (R4, provisoire). Contrat : `v4/docs/SETUP_4_1_0.md`.
- **Non couvert** : preuve d'installation réelle sur compte vierge (sous GO), mesure de la clause D1 pour le
  profil lexical, preuve du localisateur sur wheel installé. Aucune mesure de parité lexical/sémantique n'a
  été exécutée.

Contrat : `v4/docs/LEXICAL_PROFILE_4_1_0.md`.
