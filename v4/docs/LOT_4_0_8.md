## 1. Provenance : contrat et diagnostic

`MutationIn` accepte maintenant `client_provenance` ; les modèles de tâches/CAS
conservent leur déclaration propriétaire distincte. Le relais vérifie le schéma
annoncé par l'amont et remplace la provenance fournie dans les arguments par le
`clientInfo` du client aval pour TOUTES ses mutations connues, y compris les
opérations de maintenance (leur autorisation n'est pas modifiée). Un ancien
serveur n'annonçant pas le champ ne le reçoit pas. Aucun auteur n'est inféré du
texte, du chemin, du propriétaire d'une tâche ou du nom de l'application HTTP.

Déclaration courante :

```json
{"client_provenance":{"client_id":"claude-code","client_version":"<version déclarée>"}}
```

Chaque événement `change_events.changed_by` ajoute `authenticated:false`.
Le serveur direct accepte une déclaration explicite ; son absence reste `unknown`.
`authenticated:true` en entrée est refusé par les modèles. Le relais écrase les
prétentions du modèle, mais `clientInfo` demeure déclaratif, jamais authentifié.
Les reçus explicites rejoués n'ajoutent pas d'événement. Les anciennes empreintes
des opérations nouvellement enrichies restent compatibles en absence du champ.
Un nouvel auteur/payload sur une ancienne clé peut légitimement produire un
conflit : ne jamais contourner un statut incertain par une relance.

**L'événement historique 2 n'est pas réécrit.** Le code f003c3a injectait DÉJÀ
la provenance pour `memory_chat_save` ET `memory_add_facts`. Une déclaration
non vide atteint bien le journal pour un chat sans faits dans le test direct et
le test du chemin relais. L'événement `unknown` ne prouve donc pas à lui seul
un défaut du handler chat. Il faut vérifier, sur une fixture privée, le relais
réellement lancé, son catalogue et le `clientInfo` envoyé par ce client. Ne pas
attribuer rétrospectivement l'événement à Claude sur la seule base de son texte.
La lacune certaine corrigée ici : forget/bloc classique et autres mutations
n'acceptaient/ne recevaient pas systématiquement la déclaration.

Tests : sept écritures effectives (chat sans faits, ajout, oubli, bloc simple,
bloc CAS, création et mise à jour de tâche) vérifiées jusque dans `change_events`,
par relais simulé, serveur direct et auteur absent. Chaque mutation du catalogue
est aussi testée pour l'injection et le refus de prétention d'authentification.
Un test TCP supplémentaire exerce les sept écritures via le vrai SDK et relais.

## 3. Readiness : coût et cache borné

L'audit 4.0.7 est exhaustif à chaque GET : SQLite quick_check/FK, sommes et
versions historiques, têtes, métadonnées, tâches/journal, reconstruction de
vérification des blocs/reçus ; descripteur installé relu et rehaché. Aucun encodage
n'est requis pour ce travail.

Changement : cache des SEULS audits positifs SQLite et du descripteur installé,
**maximum une seconde, non prolongeable** par un appel. Aucun cache de la réponse
HTTP entière, aucun cache d'un échec. Les méthodes explicites `check_integrity`
et `build_descriptor.verify` sans option restent exhaustives (doctor/backup).
JSONL garde ses audits exhaustifs à chaque appel.

SQLite : clé = génération locale des transactions + total_changes + data_version
+ stat DB/WAL/SHM (device, inode, mode, taille, mtime_ns, ctime_ns). Toute transaction
externe au lot de sous-transactions invalide avant BEGIN, même en cas de refus,
rollback ou commit incertain ; une modification externe invalide également.
Une transaction ouverte est non prête. Une source instable entre les deux prises
d'empreintes est refusée. La fin d'un audit valide ne permet pas d'acquitter une
mutation : les transactions et leurs reçus restent indépendants de ce cache.

À chaque GET : lease, moteur ouvert/non empoisonné, erreurs d'index, modèle requis
chargé, couverture exacte des quatre index, identité/profil/capacités actuels.
L'inventaire stat du payload installé détecte ajouts/suppressions/remplacements
sans attendre le TTL. Un défaut purement mémoire non suivi par le chemin des
écritures peut n'être détecté qu'à l'expiration, **≤1 s** ; il ne faut pas présenter
ce contrat comme une relecture exhaustive instantanée à chaque GET.
Cette borne est exposée par `capabilities.readiness_audit`. Elle concerne la
readiness, jamais l'intégrité transactionnelle, l'autorisation ou les sauvegardes.
